# Чек-лист пропущенных документов (DocSync Guard)

## Обзор

Этот чек-лист используется для проверки, что при изменении кода также обновлена соответствующая документация.

## Процедура проверки

1.  **Получить список измененных файлов из `artifact_manifest`**.
2.  **Для каждого измененного файла определить тип изменения**:
    *   `.py`: Изменение логики Python.
    *   `.sql`: Изменение схемы или миграции БД.
    *   `.md`: Изменение документации.
    *   Другие типы файлов.
3.  **Проверить, требует ли тип изменения обновления документации**:
    *   `.py`: Требует обновления, если это публичный API, изменение схемы данных, изменение бизнес-логики.
    *   `.sql`: Требует обновления документации по схеме БД.
    *   `.md`: Сам по себе не требует дополнительной документации, но может повлиять на другие документы.
    *   Другие типы файлов: Оценить индивидуально.
4.  **Сопоставить измененные файлы с документами**:
    *   Изменения в `app/api/`: Проверить `docs/API-*.md`.
    *   Изменения в `app/db/`: Проверить `docs/Schema-*.md`.
    *   Изменения в `app/logging_helpers.py`: Проверить `docs/Logging-*.md`.
    *   Изменения в `app/agents/prompts/`: Проверить соответствующие промпты в документации.
    *   Добавление новых модулей: Требуется создание новой документации.
5.  **Создать список пропущенных документов**:
    *   Если для измененного файла требуется документация, но она не была обновлена, добавить документ в список пропущенных.
6.  **Создать задачу для Scribe**:
    *   Если список пропущенных документов не пуст, создать задачу `missing_docs` с указанием этих документов.

## Типы файлов и соответствующие документы

| Тип файла | Расположение | Требуемая документация |
| :--- | :--- | :--- |
| `.py` | `app/api/` | `docs/API-*.md` |
| `.py` | `app/db/` | `docs/Schema-*.md`, `docs/DB-*.md` |
| `.py` | `app/logging_helpers.py` | `docs/Logging-*.md` |
| `.py` | `app/agents/prompts/` | `docs/Prompts-*.md` или встроенные комментарии |
| `.sql` | `app/db/migrations/` | `docs/Schema-*.md` |
| `.md` | `docs/` | Может повлиять на другие документы, требует пересмотра связанных документов |

## Примеры

### Пример 1: Изменение API

*   **Измененный файл**: `app/api/orchestrator_v2.py`
*   **Тип изменения**: Добавлен новый эндпоинт `GET /tasks`.
*   **Требуемая документация**: `docs/API-Orchestrator-001.md` (или новый файл, если это значительное изменение).
*   **Проверка**: Убедиться, что документация обновлена с описанием нового эндпоинта, его параметров, кодов ответов и примеров.

### Пример 2: Изменение схемы БД

*   **Измененный файл**: `app/db/migrations/versions/abc123_add_new_column.py`
*   **Тип изменения**: Добавлен новый столбец в таблицу `features`.
*   **Требуемая документация**: `docs/Schema-000-base-tables.md`.
*   **Проверка**: Убедиться, что документация обновлена с описанием нового столбца, его типа и назначения.

### Пример 3: Изменение логики

*   **Измененный файл**: `app/orchestrator/loop.py`
*   **Тип изменения**: Изменен алгоритм выборки задач.
*   **Требуемая документация**: `docs/Architecture.md`, `docs/Ops.md`.
*   **Проверка**: Убедиться, что документация обновлена с описанием нового алгоритма и его влияния на систему.

## Автоматизация

В будущем можно рассмотреть возможность автоматизации этой проверки:

1.  Анализ diff изменений.
2.  Сопоставление измененных файлов с шаблонами, требующими документации.
3.  Проверка, были ли обновлены соответствующие документы.
4.  Автоматическое создание задачи `missing_docs` при обнаружении пропущенной документации.

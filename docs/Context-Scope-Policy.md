# Политика контекстного scope

## Общие положения

Этот документ описывает уровни доступа к контенту для различных ролей в системе, определяя, какой контекст доступен каждой роли для выполнения своих задач.

## Уровни доступа к контенту

### LOCAL (только релевантный код/схемы)

**Описание**: Минимальный контекст, необходимый для выполнения конкретной задачи. Включает только те файлы и схемы, которые непосредственно связаны с текущей задачей.

**Характеристики**:
- Только релевантный код и схемы
- Ограниченный набор файлов по селекторам
- Минимальный размер контекста
- Высокая скорость загрузки

**Использование**:
- Используется для узких задач с четко определенной областью
- Подходит для Dev, QA и Scribe при выполнении специфических задач

### PROJECT (вся капсула)

**Описание**: Полный контекст проекта, включающий все файлы, схемы и документацию, относящиеся к текущему проекту.

**Характеристики**:
- Вся капсула контекста проекта
- Все схемы БД
- Все API документация
- Все внутренние документы проекта

**Использование**:
- Используется для широких задач, требующих понимания архитектуры проекта
- Подходит для Architect и Maintainer при планировании и анализе

### EXTENDED (архив доков/чейнджлогов)

**Описание**: Расширенный контекст, включающий архивную документацию, changelog и историю изменений.

**Характеристики**:
- Архивная документация
- История изменений (changelog)
- Документы по предыдущим фичам
- Исторические решения и обоснования

**Использование**:
- Используется для глубокого анализа и понимания исторического контекста
- Подходит для Architect при сложном планировании
- Может использоваться Maintainer для понимания исторических решений

## Дефолтные scope для ролей

### Maintainer
- **Дефолтный scope**: PROJECT
- **Обоснование**: Maintainer должен понимать общую архитектуру проекта для корректной нормализации intent и определения границ задачи
- **Возможность изменения**: Может быть расширен до EXTENDED при необходимости глубокого анализа исторического контекста

### Architect
- **Дефолтный scope**: PROJECT
- **Обоснование**: Architect должен видеть всю архитектуру проекта для проектирования согласованных решений
- **Возможность изменения**: Может быть расширен до EXTENDED при необходимости анализа исторических решений

### Dev
- **Дефолтный scope**: LOCAL + выданные артефакты
- **Обоснование**: Dev должен фокусироваться на конкретной задаче и иметь доступ только к релевантному коду
- **Возможность изменения**: Может быть расширен до PROJECT при сложных задачах, требующих понимания архитектуры

### QA
- **Дефолтный scope**: LOCAL + выданные артефакты
- **Обоснование**: QA должен тестировать конкретный артефакт и иметь доступ к соответствующим тестам и схемам
- **Возможность изменения**: Может быть расширен до PROJECT при интеграционном тестировании

### Scribe
- **Дефолтный scope**: LOCAL + выданные артефакты
- **Обоснование**: Scribe должен документировать конкретный артефакт и иметь доступ к соответствующей документации
- **Возможность изменения**: Может быть расширен до PROJECT при создании архитектурной документации

## Управление контекстом

### Селекторы контекста

Для каждого уровня контекста используются специфические селекторы:

**LOCAL селекторы**:
```json
{
  "type": "code",
  "filters": {
    "module_path": "app/api/sales_report",
    "symbol": "SalesReportAPI"
  },
  "top_k": 3
}
```

**PROJECT селекторы**:
```json
{
  "type": "code",
  "filters": {
    "module_path": "app/api"
  },
  "top_k": 10
}
```

**EXTENDED селекторы**:
```json
{
  "type": "docs",
  "filters": {
    "tags": ["architecture", "history"]
  },
  "top_k": 5,
  "since": "2024-01-01T00:00:00Z"
}
```

### Ограничения

1. **Ограничение по количеству документов**: ≤ 8 документов в Scoped Pack
2. **Ограничение по токенам**: Суммарно ≤ 3k токенов
3. **Таймаут выборки**: 2 секунды

## Логирование и мониторинг

### События контекста

**context_scope_selected**:
```json
{
  "event": "context_scope_selected",
  "role": "Dev",
  "scope": "LOCAL",
  "task_id": "task_12345",
  "documents_count": 5,
  "tokens_used": 2500
}
```

**context_scope_changed**:
```json
{
  "event": "context_scope_changed",
  "role": "Architect",
  "from_scope": "PROJECT",
  "to_scope": "EXTENDED",
  "reason": "historical_analysis_needed",
  "task_id": "task_67890"
}
```

## Best Practices

1. **Используйте минимально необходимый scope**: Для повышения производительности и снижения затрат используйте минимально необходимый уровень контекста
2. **Регулярно пересматривайте scope**: При изменении требований задачи пересматривайте необходимый уровень контекста
3. **Документируйте изменения scope**: Все изменения scope должны быть задокументированы и обоснованы
4. **Мониторьте использование токенов**: Следите за использованием токенов в контексте и оптимизируйте при необходимости

## Политики безопасности

1. **Запрет на доступ к секретам**: Независимо от уровня контекста, секреты и чувствительная информация должны быть отфильтрованы
2. **Аудит доступа**: Все запросы контекста логируются для аудита
3. **Ограничение по времени**: Доступ к расширенному контексту может быть ограничен по времени для предотвращения злоупотреблений

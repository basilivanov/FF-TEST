# Monitoring and Logging Guide

## Обзор

Этот документ описывает подход к мониторингу и логированию Feature Factory.

## Логирование

### Стандарт логирования

Feature Factory следует стандарту логирования Logging-001, который определяет:
- Формат логов (JSON одной строкой)
- Обязательные поля
- Каталог событий
- Профили ключей-значений (kv)
- Уровни логирования
- Маскирование чувствительных данных
- Корреляцию запросов
- Вспомогательные инструменты

### Формат логов

Каждая запись лога представляет собой JSON объект в одной строке:

```json
{
  "ts": "2023-08-21T10:30:00.123456Z",
  "level": "INFO",
  "env": "test",
  "component": "orchestrator",
  "agent_role": "Orchestrator",
  "run_id": "run-001",
  "task_id": "task-001",
  "correlation_id": "corr-abc123",
  "event": "job_started",
  "kv": {
    "job_id": "job-001",
    "job_type": "feature_generation"
  }
}
```

### Обязательные поля

- `ts`: Временная метка в формате ISO 8601
- `level`: Уровень логирования (DEBUG, INFO, WARNING, ERROR, CRITICAL)
- `env`: Окружение (test, prod)
- `component`: Компонент системы
- `agent_role`: Роль агента
- `run_id`: Идентификатор запуска
- `task_id`: Идентификатор задачи
- `correlation_id`: Идентификатор корреляции
- `event`: Событие
- `kv`: Дополнительные ключи-значения

### Уровни логирования

- **DEBUG**: Отладочная информация (≤5% записей)
- **INFO**: Информационные сообщения (по умолчанию)
- **WARNING**: Предупреждения
- **ERROR**: Ошибки (с stack trace)
- **CRITICAL**: Критические ошибки

### Компоненты

- `orchestrator`: Оркестратор
- `llm_router`: Маршрутизатор LLM
- `validator`: Валидатор
- `executor`: Исполнитель
- `indexer`: Индексер
- `api`: API сервер
- `db`: База данных
- `cli`: CLI инструменты

### Роли агентов

- `Orchestrator`: Оркестратор
- `Architect`: Архитектор
- `Dev`: Разработчик
- `QA`: Тестировщик
- `Scribe`: Документатор
- `Maintainer`: Сопровождающий
- `System`: Системные события

### События

#### Общие события

- `job_scheduled`: Задача запланирована
- `job_started`: Задача начата
- `job_finished`: Задача завершена
- `retry_scheduled`: Повторный запуск запланирован
- `rate_limited`: Превышен лимит запросов
- `error`: Ошибка

#### HTTP события

- `api_call_start`: Начало API вызова
- `api_call_end`: Завершение API вызова

#### БД события

- `db_upsert`: Вставка/обновление записи
- `db_replace_batch`: Замена батча записей
- `db_migration_applied`: Применена миграция

#### LLM события

- `llm_call_start`: Начало вызова LLM
- `llm_call_end`: Завершение вызова LLM
- `llm_budget_exceeded`: Превышен бюджет токенов
- `llm_output_invalid`: Некорректный вывод LLM

#### ETL события

- `extract_page`: Извлечена страница данных
- `transform_batch`: Трансформирован батч данных
- `load_batch`: Загружен батч данных
- `watermark_advanced`: Продвинута watermark

#### Sheets события

- `sheets_write_start`: Начало записи в Sheets
- `sheets_write_end`: Завершение записи в Sheets

#### Docs/Change события

- `artifact_applied`: Применен артефакт
- `doc_updated`: Обновлен документ
- `changelog_written`: Записан changelog
- `index_updated`: Обновлен индекс

### Маскирование данных

Чувствительные данные маскируются:
- Токены/секреты/PII → `***REDACTED***`
- Payload не логируется

### Корреляция запросов

Все логи связаны через:
- `correlation_id`: На входе HTTP/джобы
- `run_id`: На весь конвейер
- `task_id`: На конкретную задачу

### Вспомогательные инструменты

#### Декораторы

- `@log_job`: Для джоб
- `@log_http`: Для HTTP вызовов
- `@log_db`: Для БД операций
- `llm_log_context()`: Для LLM вызовов

#### Middleware

- `CorrelationIdMiddleware`: Для сквозной корреляции запросов

## Мониторинг

### Метрики

#### API метрики

- Время отклика
- Количество запросов по статусам
- Количество ошибок
- Rate limiting события

#### LLM метрики

- Количество вызовов по моделям
- Использование токенов по ролям
- Время отклика
- Количество cache hit/miss
- Превышения бюджета

#### БД метрики

- Время выполнения запросов
- Количество конфликтов
- Размер базы данных

#### ETL метрики

- Количество обработанных записей
- Время обработки
- Количество ошибок
- Watermark прогресс

#### Индекс метрики

- Размер индекса
- Время обновления
- Количество индексируемых файлов

### Health Checks

#### Liveness Probe

`GET /api/v1/health/live`

Проверяет, что приложение запущено.

#### Readiness Probe

`GET /api/v1/health/ready`

Проверяет, что приложение готово к приему запросов:
- База данных доступна
- Миграции применены
- Индексные файлы существуют

#### Dependencies Probe

`GET /api/v1/health/deps`

Проверяет зависимости:
- CLI бинарники доступны
- Внешние API доступны

### Алерты

#### Критические алерты

- API недоступен
- База данных недоступна
- Превышено количество ошибок
- Превышен бюджет токенов

#### Предупреждения

- Высокое время отклика API
- Низкий уровень успеха задач
- Приближение к лимитам токенов

### Dashboards

#### Системный дашборд

- Состояние API
- Состояние базы данных
- Состояние индекса
- Количество активных задач
- Количество ошибок

#### Бизнес-дашборд

- Количество созданных фич
- Скорость обработки задач
- Время выполнения графов
- Количество обработанных записей

#### LLM дашборд

- Использование токенов по ролям
- Использование токенов по моделям
- Время отклика LLM
- Количество вызовов
- Количество cache hit/miss

#### Финансовый дашборд

- Стоимость использования LLM
- Бюджеты по ролям
- Прогноз расходов

Измеряется время выполнения API вызовов:
- Время обработки запроса
- Время выполнения бизнес-логики
- Время работы с базой данных
- Время вызовов внешних API

### Профилирование LLM

Измеряется время вызовов LLM:
- Время подготовки запроса
- Время выполнения LLM
- Время обработки ответа

### Профилирование БД

- Время подготовки запроса
- Время выполнения запроса
- Время обработки результата

## Логирование в реальном времени

### Server-Sent Events

Для передачи логов в реальном времени используется Server-Sent Events:
- Подключение к `/api/v1/stream/events`
- Получение событий: `job_started`, `job_finished`, `error`, `index_updated`, `doc_updated`, `llm_call_end`

### Формат SSE событий

```
event: job_started
data: {"job_id": "job-001", "task_id": "task-001", "run_id": "run-001", "correlation_id": "corr-abc123"}

event: job_finished
data: {"job_id": "job-001", "task_id": "task-001", "run_id": "run-001", "correlation_id": "corr-abc123", "result": "success"}
```

## Хранение логов

### Локальное хранение

Логи хранятся в директории `logs/`:
- `app.log`: Основные логи приложения
- `api.log`: Логи API
- `llm.log`: Логи LLM
- `db.log`: Логи БД
- `error.log`: Логи ошибок

### Ротация логов

Логи ротируются:
- По размеру (100MB)
- По времени (ежедневно)
- Хранение 30 дней

### Архивирование логов

Старые логи архивируются:
- Сжатие gzip
- Хранение 90 дней
- Архивы перемещаются в `logs/archive/`

## Анализ логов

### ELK стек

Для анализа логов может использоваться ELK стек:
- Elasticsearch для хранения
- Logstash для обработки
- Kibana для визуализации

### Примеры запросов

#### Поиск ошибок

```
level: ERROR AND component: orchestrator
```

#### Анализ времени отклика

```
event: api_call_end AND kv.duration_ms:>1000
```

#### Мониторинг использования токенов

```
event: llm_call_end AND kv.input_tokens:>10000
```

## Best Practices

### Логирование

1. **Всегда логируйте начало и завершение операций**
2. **Используйте соответствующие уровни логирования**
3. **Включайте контекст в логи**
4. **Маскируйте чувствительные данные**
5. **Используйте корреляционные ID**
6. **Логируйте ошибки с stack trace**

### Мониторинг

1. **Определяйте ключевые метрики**
2. **Настраивайте алерты на критические метрики**
3. **Создавайте дашборды для визуализации метрик**
4. **Регулярно пересматривайте метрики и алерты**
5. **Используйте трендовые анализы**
6. **Проводите пост-мортем анализ инцидентов**

### Профилирование

1. **Профилируйте критические пути**
2. **Измеряйте время выполнения операций**
3. **Оптимизируйте медленные операции**
4. **Используйте кэширование при возможности**
5. **Мониторьте использование ресурсов**
6. **Проводите нагрузочное тестирование**

## Troubleshooting

### Проблемы с логированием

#### Логи не записываются

1. Проверьте права доступа к директории логов
2. Проверьте свободное место на диске
3. Проверьте конфигурацию логгера

#### Логи не содержат нужной информации

1. Проверьте уровень логирования
2. Проверьте формат логов
3. Проверьте фильтры логгера

### Проблемы с мониторингом

#### Метрики не обновляются

1. Проверьте доступность эндпоинтов метрик
2. Проверьте конфигурацию сбора метрик
3. Проверьте сетевые настройки

#### Алерты ложно срабатывают

1. Проверьте условия алертов
2. Проверьте временные окна
3. Проверьте пороговые значения

### Проблемы с профилированием

#### Профилирование влияет на производительность

1. Используйте sampling
2. Минимизируйте объем собираемых данных
3. Отключайте профилирование в продакшене

# QA Policy 001 — Требования к тестированию

## Запрещённые практики — список с regex-примерами, например:

assertIn\(response\.status_code, \[.*200.*\] → запрещено

requests\.post\( в юнитах без TestClient → запрещено

:memory: / произвольные имена БД в тестах → запрещено

mock\.return_value\.* в тестах API → запрещено (использовать side_effect)

print\( в тестах → запрещено (использовать assert с сообщениями)

response\.json\(\) без валидации по JSON-схеме → запрещено

## Обязательные проверки — статусы, JSON-схемы, запись в БД, логи (event-коды).

## Шаблон тест-кейса — Given/When/Then; фикстура БД; фикстура capsule_system_prompt.

## Политика Gate — нарушение → qa_policy_violation + причины.

## Требования к API-тестам

### Структура тестов API
- Каждый эндпоинт должен иметь минимум 3 теста:
  1. Успешный сценарий
  2. Ошибка 404 (если применимо)
  3. Ошибка валидации входных данных

### Проверка JSON-схем
- Все ответы API должны соответствовать определенным JSON-схемам
- Использовать jsonschema.validate для проверки соответствия

### Проверка логов
- Каждый вызов API должен логировать события api_call_start и api_call_end
- Логи должны содержать correlation_id для корреляции

### Проверка БД
- После успешных операций состояние БД должно соответствовать ожидаемому
- Использовать прямые SQL-запросы для проверки состояния БД

### Mock-объекты
- Использовать unittest.mock для мокирования внешних зависимостей
- Не мокировать внутренние компоненты без крайней необходимости

## Code Coverage
- Минимальное покрытие для критических путей: 70%
- Покрытие API-эндпоинтов: 100%
- Покрытие бизнес-логики: 80%
